# 开发流程

## 1. 流程概览

本项目采用“功能分支开发、Pull Request 合并、Build 校验、Draft Release、正式 Release 发布”的流程。依赖更新单独由 Dependabot 处理，先进入依赖更新分支，再由开发者决定是否合并到功能分支或 `main`。

完整链路如下：

1. 从目标基线创建功能分支。
2. 在功能分支修改代码、补充文档并使用 IDEA MCP 编译验证。
3. 推送分支并创建 Pull Request。
4. 通过 Build、测试、代码检查和插件验证。
5. 将 Pull Request 合并到 `main`。
6. Build 在 `main` 上生成 Draft Release。
7. 检查 Draft Release 内容，发布为正式 Release 或预发布 Release。
8. Release 工作流根据 tag 构建、签名、发布插件并上传发行资产。
9. Release 工作流自动创建 CHANGELOG 更新 Pull Request，单独合并。

## 2. 分支与 Checkout

### 2.1 获取最新远程信息

```bash
git fetch origin --prune
git branch -a
```

### 2.2 开发新功能

功能从 `main` 开始时：

```bash
git switch main
git pull --ff-only origin main
git switch -c feat/1.0.3
```

当前工作的功能分支就是 `feat/1.0.3`。如果继续已有分支：

```bash
git switch feat/1.0.3
git pull --ff-only origin feat/1.0.3
```

历史 Pull Request 证明了类似的版本分支流程：PR #74 使用 `feat/1.0.2` 作为 head，之后进入 `releases/1.0.2`；PR #76 再将版本分支合并到 `main`。

证据：[已关闭 Pull Requests](https://github.com/wx98/km-quick-mybatis/pulls?q=is%3Apr+is%3Aclosed)。

### 2.3 依赖更新分支

Dependabot 的目标分支应使用不会占用 `dependabot/` 命名空间的名称，例如 `dependabot-updates`：

```bash
git switch main
git pull --ff-only origin main
git switch -c dependabot-updates
```

`.github/dependabot.yml` 中的 `target-branch` 决定更新 PR 的目标分支；它不是 Dependabot 自动生成的单个更新分支名称。`dependabot` 作为顶层分支会与 Dependabot 生成的 `dependabot/...` 分支产生 Git ref 命名空间冲突，因此不应继续作为 target branch。

## 3. 修复与本地验证

1. 在功能分支定位 Issue、异常日志和受影响模块。
2. 阅读调用链、生命周期和已有测试，保持修改范围与现有架构一致。
3. 修改代码，同时更新必要的设计文档。
4. 在 IDEA 中通过项目 MCP 执行编译；本项目约定使用 IDEA MCP，不以命令行 Gradle 编译作为主要验证方式。
5. 检查 Git 差异和状态：

```bash
git diff
git status --short
```

6. 提交一个清晰、可追溯的 commit：

```bash
git add <修改文件>
git commit -m "fix: <修复内容>"
```

7. 推送功能分支：

```bash
git push -u origin feat/1.0.3
```

本次分支上的修复提交为 `69134b1`，主题是 `fix: harden plugin cache lifecycle and Dependabot updates`；提交前已经通过 IDEA MCP 项目编译。

## 4. Pull Request 合并

在 GitHub 创建 PR 时：

1. 普通功能选择 `feat/1.0.3 -> main`。
2. 版本发布可先选择 `feat/1.0.3 -> releases/1.0.3`，完成版本确认后再合并到 `main`。
3. Dependabot 更新先选择 `dependabot-updates -> main`，检查依赖变更后再决定是否纳入功能分支。
4. 等待 Build、Test、Inspect、Verify 全部通过。
5. 查看变更、评论和冲突，确认没有未处理的异常或回归。
6. 使用 Squash 或 Merge 完成合并，并删除已完成的临时分支。

历史证据：PR #64、#68 的 head 都是 `dependabot`，base 是 `main`；PR #83 和 #82 是 Dependabot 独立依赖更新 PR；PR #74、#76 展示了版本分支到 `main` 的发布前合并路径。

## 5. Build 自动校验与 Draft Release

Build 工作流配置在 `.github/workflows/build.yml`，触发条件是：

- push 到 `main`；
- 任意 Pull Request；
- 手动 `workflow_dispatch`。

Build 工作流依次执行：

1. Checkout 源码并校验 Gradle Wrapper。
2. 设置 Java 17 Zulu 和 Gradle。
3. 从 `gradle.properties` 读取版本。
4. 读取 `CHANGELOG.md` 的 Unreleased 内容。
5. 执行 `buildPlugin` 构建插件。
6. 执行 `check` 测试，并在失败时上传报告。
7. 执行 Qodana 代码检查。
8. 执行 Plugin Verifier 兼容性验证。
9. 在非 Pull Request 事件且前置任务都通过时，删除旧 Draft Release，并创建新的 `v<version>` Draft Release。

历史证据：[Build workflow runs](https://github.com/wx98/km-quick-mybatis/actions/workflows/build.yml)。其中 Build #127 对应 PR #74（`feat/1.0.2`），Build #130 对应 `releases/1.0.2`，Build #137 对应提交 `f92da2d`，Build #140 对应 `main` 上的 CHANGELOG 更新。

## 6. 创建并发布 Release

### 6.1 检查 Draft Release

合并到 `main` 后打开 GitHub Releases，检查：

- 版本号是否为 `v1.0.3`；
- Release notes 是否来自 CHANGELOG 的 Unreleased；
- tag 是否指向预期的 `main` 提交；
- 构建是否已成功完成。

确认无误后，将 Draft Release 发布为正式 Release；需要提前验证时可以发布为 Pre-release。

### 6.2 Release 工作流行为

`.github/workflows/release.yml` 的触发条件是：

```yaml
on:
  release:
    types: [ prereleased, released ]
```

Release 工作流执行以下步骤：

1. Checkout `github.event.release.tag_name` 指向的 tag，而不是默认分支。
2. 设置 Java 17 Zulu 和 Gradle。
3. 读取 Release body 作为 changelog。
4. 有 Release notes 时执行 `patchChangelog`，将内容写入 CHANGELOG。
5. 使用 `PUBLISH_TOKEN`、`CERTIFICATE_CHAIN`、`PRIVATE_KEY`、`PRIVATE_KEY_PASSWORD` 执行 `publishPlugin`，发布到 JetBrains Marketplace。
6. 使用 `GITHUB_TOKEN` 将 `build/distributions/*` 上传到当前 GitHub Release。
7. 有 changelog 时创建 `changelog-update-v<version>` 分支，提交 `CHANGELOG.md`，创建带 `release changelog` 标签的 PR。

Release 工作流需要的 Secrets：

- `PUBLISH_TOKEN`
- `CERTIFICATE_CHAIN`
- `PRIVATE_KEY`
- `PRIVATE_KEY_PASSWORD`
- `PAT_TOKEN`（创建 CHANGELOG PR）

历史证据：[Release workflow runs](https://github.com/wx98/km-quick-mybatis/actions/workflows/release.yml) 显示 Release #9 由 `v1.0.2` 发布事件触发并成功完成；源码证据：[release.yml](https://github.com/wx98/km-quick-mybatis/blob/main/.github/workflows/release.yml)。

## 7. Tag、Release 与插件资产的关系

三者关系如下：

1. `main` 上的版本提交触发 Build 创建 Draft Release。
2. Draft Release 使用 `v<version>` tag，例如 `v1.0.2`。
3. 发布 Release 后触发 Release workflow。
4. Release workflow checkout 该 tag，构建的插件内容因此与 Release tag 固定对应。
5. 构建产物上传回同一个 Release 页面。

历史 Tags：[Tags](https://github.com/wx98/km-quick-mybatis/tags)：`v1.0.2` 指向 `f92da2d`，`v1.0.1` 指向 `4d9e51a`，`v1.0.0` 指向 `d122f3f`。历史 Releases：[Releases](https://github.com/wx98/km-quick-mybatis/releases)：v1.0.2 页面包含 `km-quick-mybatis-1.0.2-signed.zip` 和普通 zip 资产，说明 Release workflow 已完成构建产物上传。

## 8. CHANGELOG 联动

发布前：

1. 在 `CHANGELOG.md` 的 `Unreleased` 中维护本次功能和修复。
2. Build 将 Unreleased 内容写入 Draft Release notes。
3. 发布 Release 时，Release workflow 读取 Release body。
4. `patchChangelog` 将本次 notes 写入对应版本区段。
5. 自动创建 `changelog-update-v1.0.3` PR。
6. 检查后合并该 PR，确保 `CHANGELOG.md` 与 Release 保持一致。

历史证据：Build #139 对应 `changelog-update-v1.0.2` PR #79，Build #140 对应合并后的 main 提交 `35f46bd`；Release 页面 v1.0.2 的 notes 关联 PR #74，形成了“版本开发 PR -> Release -> CHANGELOG PR”的闭环。

## 9. Dependabot 的推荐操作流程

1. 将 `.github/dependabot.yml` 的两个 ecosystem 都设置为 `target-branch: "dependabot-updates"`。
2. 保持 Gradle 和 GitHub Actions 更新都进入该分支。
3. Dependabot 产生更新 PR 后，先在 `dependabot-updates` 上汇总和验证。
4. 由开发者创建或合并 `dependabot-updates -> feat/1.0.3` 的 PR，将依赖更新纳入当前开发工作。
5. 功能完成后再通过 `feat/1.0.3 -> main` 的 PR 合并。

当前失败运行的浏览器证据：[Dependabot failed job](https://github.com/wx98/km-quick-mybatis/actions/runs/34992855506/job/104461612655) 明确显示：顶层分支 `dependabot` 已占用 `dependabot/` ref 命名空间，Git 无法创建新的 `dependabot/...` 更新分支。历史成功运行和 PR #64、#68 只能证明旧流程曾经成功，不能证明该命名仍适合创建新的更新分支。

## 10. 一次完整发布示例

```bash
git switch main
git pull --ff-only origin main
git switch -c feat/1.0.3
# 修改代码、CHANGELOG.md 和 docs
git add .
git commit -m "feat: prepare 1.0.3 release"
git push -u origin feat/1.0.3
```

然后在 GitHub：

1. 创建 `feat/1.0.3 -> main` PR。
2. 等待 Build 全部检查通过并合并。
3. 在 Draft Release 中确认 `v1.0.3` 和 Release notes。
4. 发布 `v1.0.3`。
5. 等待 Release workflow 完成 Marketplace 发布和资产上传。
6. 合并自动创建的 `changelog-update-v1.0.3` PR。
7. 在 Tags、Releases 和 Actions 中核对 tag、运行结果和 zip 资产。

完成后，代码、插件市场版本、Git tag、GitHub Release、CHANGELOG 和构建记录彼此对应。

## 11. 实际执行顺序

### 11.1 开始一个普通功能

按下面顺序执行，不要跳过基线同步：

1. 在 IDEA Terminal 中执行 `git switch main`。
2. 执行 `git pull --ff-only origin main`；如果出现本地提交或冲突，先停止，不要直接强制合并。
3. 执行 `git switch -c feat/1.0.3`，分支名按实际版本或功能替换。
4. 修改代码和文档。
5. 使用 IDEA MCP 执行 Build Project，确认编译成功。
6. 查看 `git diff`，确认没有修改 README、密钥或无关文件。
7. 提交并推送分支。
8. 在 GitHub 创建 PR，目标分支为 `main`。
9. 只有当 Build 的 Test、Inspect、Verify 都通过后，才合并 PR。

### 11.2 处理一个 Bug

1. 打开 Issue，先查看 Issue 正文和全部评论，尤其搜索 `Exception`、`Caused by`、`ERROR`、`stacktrace`。
2. 记录异常的入口、触发条件、受影响版本和预期行为。
3. 在 `feat/1.0.3` 上复现问题，确定是代码问题、配置问题还是环境问题。
4. 修改最小必要范围，并补充能够覆盖回归场景的验证。
5. 用 IDEA MCP 编译；编译失败就留在当前分支修复，不要创建 PR。
6. 提交时使用能说明行为变化的消息，例如 `fix: prevent cache access after project close`。
7. 推送后回到 PR 页面查看新的 Build 运行和所有评论。
8. 只有异常消失且相关检查通过，才合并。

### 11.3 处理 Dependabot 更新

1. 先确认 `.github/dependabot.yml` 的 `target-branch` 是 `dependabot-updates`。
2. 确认远程存在该分支：`git ls-remote --heads origin dependabot-updates`。
3. 在 Actions 的 Dependabot Updates 页面手动运行一次，或等待下一个计划周期。
4. 如果生成 PR，先确认 base 是 `dependabot-updates`，不要把它直接合并到 `main`。
5. 在 `dependabot-updates` 的 PR 上查看完整 diff，并等待 Build 检查通过。
6. 要纳入当前功能时，创建 `dependabot-updates -> feat/1.0.3` 的 PR；不需要时只保留在依赖分支。
7. 功能分支验证通过后，再创建或合并 `feat/1.0.3 -> main`。
8. 如果日志出现 `Branch 'dependabot' already exists`，先改用 `dependabot-updates`，再重新运行，不要反复重试旧配置。

### 11.4 发布一个版本

1. 在 `gradle.properties` 修改 `pluginVersion`，例如改为 `1.0.3`。
2. 在 `CHANGELOG.md` 的 `Unreleased` 中写完本次变更。
3. 将功能分支提交并创建到 `main` 的 PR。
4. 等待 Build 的四类检查通过：构建、测试、Qodana、Plugin Verifier。
5. 合并 PR 后进入 Actions，确认 `main` 上的 Build 成功，并打开 Releases 页面。
6. 打开对应的 Draft Release，核对版本号、tag 提交和 Release notes。
7. 需要正式发布时点击发布 Release；需要预发布验证时选择 Pre-release。
8. 进入 Release workflow，确认 checkout 的 tag 正确、`publishPlugin` 成功、zip 资产已上传。
9. 发布完成后打开 JetBrains Marketplace 和 GitHub Release，分别确认插件版本和下载资产。
10. 最后合并自动生成的 `changelog-update-v1.0.3` PR，再检查 `main` 的 CHANGELOG。

## 12. 失败处理决策

| 现象 | 处理动作 |
| --- | --- |
| IDEA MCP 编译失败 | 留在当前功能分支，先修复编译错误，再提交或更新 PR。 |
| PR Build 失败 | 打开失败 job 的日志，定位具体步骤；修复后重新推送，GitHub 会自动重新运行。 |
| Dependabot 无法创建分支 | 检查是否存在顶层 `dependabot` 分支；将 target branch 改为 `dependabot-updates`。 |
| Draft Release 没有生成 | 检查 Build 是否来自 `main` push，以及所有依赖 job 是否成功。 |
| Release 没有触发 | 确认 Draft Release 已被发布为 `released` 或 `prereleased`，而不是仍处于 draft。 |
| Marketplace 发布失败 | 检查四个签名和发布 Secrets，不要重复创建同一版本 tag。 |
| 没有 CHANGELOG PR | 检查 Release body 是否为空，以及 `PAT_TOKEN` 是否有创建分支和 PR 的权限。 |

## 13. 发布完成检查清单

- [ ] 当前修改已经从功能分支进入目标 PR。
- [ ] IDEA MCP 编译成功。
- [ ] Build 的 Test、Inspect、Verify 成功。
- [ ] `main` 已包含预期提交。
- [ ] Draft Release 的版本号与 `pluginVersion` 一致。
- [ ] tag 指向正确的 `main` 提交。
- [ ] Release workflow 成功。
- [ ] JetBrains Marketplace 出现新版本。
- [ ] GitHub Release 存在 signed zip 和普通 zip。
- [ ] `changelog-update-v<version>` PR 已合并。
